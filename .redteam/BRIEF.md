# Red Team Brief — Бригадное Ядро Гармонизации (D:\aitraining)

## Что за система
Классическая 4-голосная гармонизация SATB по «Бригадному» учебнику (Дубовский/Евсеев/Способин/Соколов).
Стек: Python 3.14, FastAPI (`backend/`), алгоритмическое ядро (`src/harmony/`), React 19 + OSMD (`frontend/`).
Живой сервис: http://127.0.0.1:8000 (PID слушает 127.0.0.1:8000), SPA из `frontend/dist`.
Заявлено в README: 127 passing tests, «0 косяков», hard gates, Viterbi O(N*K^2), топ-3 решения, строгие правила.

## Симптом из скриншота (главный баг)
Пользователь нажал «Гармонизовать мелодию» → модальный `alert`:
«Все кандидаты отклонены жесткими правилами голосоведения.»
При этом на экране остаются СТАРЫЕ кандидаты (#1 Оптимум T→S6→D→T→D→T, cost -7; #2 T→S6→D→T→D6→T, cost -5),
кнопка в состоянии «Математический синтез (Viterbi)...», тональность C мажор, размер 4/4,
«Расширенный диапазон» выкл., «Побочные доминанты» (чекбокс) — вероятно выкл.

## Уже подтверждено (мной, лидом)
- Дефолтная мелодия фронтенда (`frontend/src/App.tsx` INITIAL_MELODY: E4 F4 G4 E4 D4 C4, half/half/half/half/half/whole, C Major, 4/4)
  через `POST /api/harmonize` УСПЕШНА: 3 кандидата, ~405 ms. То есть баг не в дефолтном сценарии, а input-dependent.
- Топ-1 кандидат содержит грубые дефекты голосоведения, которые движок не поймал:
  - такт 1: T=C3 и B=C3 — унисон тенора и баса (TB=0), при этом квинта C-трезвучия (G) отсутствует;
  - финальный аккорд: S=C4 и A=C4 — унисон сопрано и альта.
  - `src/harmony/rules/spacing.py` проверяет `S >= A >= T >= B` нестрого и не запрещает унисоны соседних голосов;
    `src/harmony/solver/state_generator.py` перебирает `b` до `min(b_max, t)` включительно → унисон B=T разрешён.
- `check_syntax` (`src/harmony/rules/engine.py:104`) запрещает D→S на ЛЮБОМ такте, без учёта метрики/проходящих оборотов.
- `backend/api.py:243` возвращает одну и ту же фразу «Все кандидаты отклонены...» независимо от реальной причины
  (нет планов / нет кандидатов на шаге / DP заблокирован); диагностика `SolverResult.message` выбрасывается.
- `backend/api.py:229` останавливает перебор после 3 успешных ПЛАНОВ, а не после 3 лучших по стоимости;
  кандидаты сортируются уже после — «топ-3» не глобально оптимальны.
- `backend/api.py:159-167`: при `allow_secondary_dominants=false`, если фильтр отсёк все планы, молча берутся все планы
  (`filtered_plans or all_plans`) — настройка игнорируется.
- `frontend/src/App.tsx:113-115`: при неуспехе старые `candidates` не очищаются, ошибка только через `alert()`;
  `resp.ok` не проверяется; при 422/500 показывается generic alert.

## Известные подозрительные места (проверить и подтвердить/опровергнуть)
1. `src/harmony/rules/voice_leading.py`:
   - `check_contrary_fifths_and_octaves` математически почти недостижим при обычных шагах (d2-d1 ≡ 0 mod 12) — мёртвый код?
   - hidden 5/8 проверяются ТОЛЬКО между S и B; между S-A и S-T не проверяются.
   - `check_melodic_intervals`: запрещены все тритоны (6), но не увеличенная квинта (8), не ум. кварта (4), не ум. септима?
   - parallel check: `d1*d2 > 0` — не ловит параллелизм, где один голос повторяется (это не параллелизм, ок), но ловит ли
     параллельные квинты через октавный скачок одного из голосов? Проверить.
   - overlap-проверка может быть сверхстрогой/неполной.
2. `src/harmony/rules/spacing.py`: диапазоны голосов (S C4-A5, A G3-D5, T C3-G4, B E2-C4) vs «Бригадный» учебник;
   extended B C2 — сомнительно; проверка `T-B <= 24` вместо классического «бас-тенор не более 1.5 октавы»?
3. `src/harmony/rules/doubling.py`: правила удвоения (терция запрещена в мажорных трезвучиях? в минорных?),
   VI после D (удвоение терции), K64 (удвоение баса), септаккорды (полные/неполные), уменьшённые трезвучия.
4. `src/harmony/rules/resolutions.py`: разрешение септимы вниз, D43→T6, D7→T, VII7→T, II7→D, альтерации.
5. `src/harmony/rules/chromatic.py`: DD, альтерации, неаполитанский, отклонения.
6. `src/harmony/rules/non_chord_tones.py`: похоже, движок НЕ умеет проходящие/вспомогательные ноты в мелодии:
   state_generator требует, чтобы сопрано было тоном аккорда. Значит любая мелодия с NCT на слабой доле
   либо не гармонизуется, либо получает бессмысленный аккорд. Это ключевая архитектурная дыра.
7. `src/harmony/syntax/grammar.py`: генерация планов, старт/финал (T), каденции, K64, прерванный оборот,
   метрические акценты, длина планов, ограничение max_plans, дедупликация.
8. `src/harmony/core/types.py`: `calculate_metric_structure` — как считаются downbeats/durations, что с 3/4, 2/4, 6/8, 3/8,
   с длительностями whole/half/quarter/eighth, с пунктирами; `TimeSignature.parse`.
9. `backend/key_detector.py`: 24 тональности, «гармонический минор», алгоритм (Krumhansl? эвристика?), ложные детекции.
10. `backend/grader.py`: оценка 5/4/3/2, пороги, согласованность с solver hard gates (grader может ругать то,
    что solver производит).
11. `backend/exporters.py`, `src/harmony/export/*`: MusicXML (voice/staff/backup/duration), MIDI (каналы, program, tempo),
    ASCII, длительности; соответствие `durations` исходной мелодии (в MusicXML видны подозрительные `duration=16` whole в такте 3,
    `backup` 24 и т.п.).
12. `frontend/src/audio/synth.ts`, `midiInput.ts`, `AudioControls.tsx`: тайминг, полифония, stop/restart, утечки.
13. `frontend/src/components/MelodyInput.tsx`: ввод, валидация, MIDI-запись, диапазоны, downbeat-флаги.
14. `frontend/src/App.tsx`: `useEffect` авто-гармонизации на маунте (в dev StrictMode — двойной вызов), alert, stale state,
    общий score между вкладками, отсутствие abort/race protection (два запроса — последний выигрывает?).
15. README/docs: заявленные «Bi-GRU», «нейро-символический», «127 tests», «0 косяков» — проверить, что реально в коде
    (models/style_weights.json — статические веса? есть ли ML?).
16. Тесты: что реально покрыто, есть ли тесты на негативные кейсы, не подгоняют ли тесты вывод под баги.
